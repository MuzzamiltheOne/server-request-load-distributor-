2. ABSTRACT & INTRODUCTION

Project Overview:
This project demonstrates an intelligent, real-time load distribution system designed to route incoming computing workloads across specialized worker servers. Instead of relying on round-robin or blind shortest-queue algorithms, the load balancer dynamically calculates the optimal server for every incoming request using a Cost-Minimization Greedy Algorithm powered by a Min-Heap Priority Queue.

Problem Background:
In distributed computing, routing requests based solely on queue lengths leads to severe bottlenecks ("Thundering Herd" problems) and poor hardware utilization. High-capacity servers may remain underutilized while lightweight servers get crushed by heavy processing tasks, or vice versa.

Proposed Solution:
A load-balancing architecture that factors in incoming request workloads alongside server-specific performance profiles (setup overheads and processing throughput). By tracking live backlogs and applying a bounded-concurrency model using semaphores, the system ensures optimal performance and prevents server crashes under heavy load.

Purpose of the Project:
To provide a concrete implementation and visualization of key Data Structures and Algorithms (DAA) concepts—specifically Greedy Choice strategies and Min-Heap Priority Queues—applied to solve real-world distributed system scheduling challenges.

5. ALGORITHMS & METHODOLOGY

System Workflow:

1. Client generates requests containing specific workload units and sends them with a 50ms rate-limited delay.
2. The Load Balancer receives the request and extracts the workload size.
3. The load balancer calculates the expected completion time across all candidate servers.
4. Candidate servers are inserted into a Min-Heap Priority Queue sorted by calculated completion time.
5. The algorithm pops the top candidate (the minimum calculated execution time).
6. The winning server's backlog is updated with the new workload.
7. The request acquires a semaphore slot; if max concurrency (3) is reached, the request stalls until a slot opens.
8. The request is proxied via HTTP POST to the assigned backend server.
9. Upon completion, the semaphore slot is freed and the server's backlog is drained.
10. Complete decision logs and mathematical proofs are returned to the user interface.

Algorithms Used:

1. Cost-Minimization Greedy Algorithm (Min-Completion-Time Scheduling):
Makes locally optimal routing decisions for each arriving request without requiring knowledge of future traffic.
2. Min-Heap Priority Queue (heapq):
Sorts server candidates by calculated execution cost, allowing O(log k) extraction of the optimal server.

The Equation:
Calculated Estimated Time (T) = Setup Time + ((Current Backlog + Incoming Workload) / Processing Speed)

Where:

* Setup Time: Fixed initialization delay in milliseconds (ms).
* Current Backlog: Pending workload units (u) queued on the server.
* Incoming Workload: Workload units (u) required by the new task.
* Processing Speed: Execution throughput (workload units per ms).

Mathematical Selection Criterion:
S_best = argmin_i ( Setup_i + ( (Backlog_i + Workload_new) / Speed_i ) )

Development Methodology:
Iterative modular development focusing on backend API design, thread safety, state locking, algorithmic correctness, and client-server integration.

Data Flow:
Client Request Payload -> Flask Distributor Endpoint -> Thread-Locked Backlog State -> Math Calculation & Priority Queue Construction -> Heap Extract Minimum -> Semaphore Acquire -> HTTP Proxy to Worker Server -> Task Execution -> Semaphore Release -> Thread-Locked Backlog Drain -> HTTP Response to Client.

7. RESULTS, TESTING & PERFORMANCE

Project Results:

* Small Workloads (e.g., 5 units): The system dynamically routes to Server C (Fast) because its 0.0ms setup delay outweighs its slower compute speed for small tasks.
* Large Workloads (e.g., 80 units): The system routes to Server A (Heavy) because its fast execution speed (10 units/ms) easily compensates for its 15.0ms setup penalty.
* Heavy Traffic Spikes: Requests beyond the 3-slot concurrency limit are held safely in a stalled state by semaphores without dropping connections or causing server crashes.
